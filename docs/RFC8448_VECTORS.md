# Published TLS record known answer

The [RFC8448 §3 Simple 1-RTT Handshake](https://www.rfc-editor.org/rfc/rfc8448.html#section-3)
server's first **protected** Handshake record is now an independent regression
for `ProtectedWriter`, `ProtectedReader` and bounded handshake `Reassembler`.
Expected ciphertext is copied from the primary RFC, not generated by AWS-LC
or our implementation. This is record-level known-answer evidence, not complete
endpoint interoperability or certificate/Finished authentication.

## Exact vector

Select `{server} derive write traffic keys for handshake data` (RFC page7),
then the second `{server} send handshake record` in §3 (RFC pages9–10), after
the unprotected ServerHello. Published `payload (657 octets)` and `complete
record (679 octets)` are the fixture labels. The declared sizes are657/679.

```text
suite:       TLS_AES_128_GCM_SHA256
traffic key: 3f ce 51 60 09 c2 17 27 d0 f2 e4 e8 6e e4 03 bc
static IV:   5d 31 3e b2 67 12 76 ee 13 00 0b 30
sequence:    0 (first protected record under server handshake traffic keys)
nonce:       static IV XOR left-zero-padded uint64(0), hence unchanged
outer AAD:   17 03 03 02 a2
inner type:  16 hexadecimal (Handshake, decimal22)
zero padding:0 bytes
sizes:       657 content +1 type +16 GCM tag =674 ciphertext;
             5 header +674 ciphertext =679 complete wire bytes
```

The published657-byte payload concatenates exactly four encoded handshake
messages, including each four-byte type/u24 header:

| Type | Message | Body bytes | Encoded bytes | Payload offset |
|---:|---|---:|---:|---:|
|8 |EncryptedExtensions |36 |40 |0 |
|11 |Certificate |441 |445 |40 |
|15 |CertificateVerify |132 |136 |485 |
|20 |Finished |32 |36 |621 |

Finished ends at byte657, exactly at the authenticated record's content
boundary. The test concatenates all `Message.encoded` outputs and compares
all657 bytes with the published payload under work budgets1/17/128/1024.
It checks the message types, body/header lengths, exact slices, consumption,
empty final accumulation and permission to cross the subsequent key boundary.
It does not compute a transcript hash or validate message semantics.

The writer compares every679 newly sealed wire bytes with the independent RFC
fixture. The reader separately opens that RFC fixture, rather than the writer's
output; it checks exact content, type, consumed length, sequence0→1 and erasure
of type/tag/unused output after success. Already-derived public test keys/IVs
are imported directly. HKDF traffic derivation is not tested here.

RFC8448 describes the original TLS1.3 specification. Its record construction
remains a useful known answer for the RFC9846 record implementation; this does
not establish conformance to newer requirements outside this vector. The
embedded historical certificate and signature are treated as opaque handshake
bytes, and are not used as trusted credentials or proof of current validity.

```sh
cargo test -p tls-core --test rfc8448_record --locked
cargo clippy -p tls-core --test rfc8448_record --locked -- -D warnings
```

Both commands pass. Additional client application/alert vectors are covered by
the protected-record integration suite; this separate fixture focuses on the
server flight and exact reassembled handshake bytes. Primitive/provider vectors
remain in `tls-crypto-awslc` tests.

## Transcript and derived-key composition

`rfc8448_composition` now composes production streaming transcript, TLS key
schedule, protected records and incremental handshake reassembly. Its inputs
are the exact published ClientHello/ServerHello, the public validated shared
secret and published ciphertext. It checks the published CH..SH hash
`860c06ed...f0e1cad8`, derives the server handshake key/IV, opens the server
flight, hashes its encoded messages, verifies server Finished against the
pre-Finished snapshot, and rejects changed hash/tag inputs. It checks the
through-server-Finished hash `9608102a...ff83df13`, derives application keys,
matches client Finished and reproduces the published client application record.


The same integration target also checks the independent RFC8448 §5 HRR trace:
ClientHello1(180), HRR(176), ClientHello2(512) and final ServerHello(123) encoded
bytes yield the published transcript hash
`8aa8e828ec2f8a884fec95a3139de01c15a3daa7ff5bfc3f4bfcc21b438d7bf8`.
The RFC labels both HRR and final hello as ServerHello. The fixture extractor
reads those four named blocks only within §5, skipping page headings and taking
exact declared octet counts. The test deliberately preloads the supplied context,
checking that transcript construction resets it before HRR rewriting. It does
not validate the P256 key shares or cookie/extension negotiation. Exact fixture
sizes and both file/decoded hashes are retained in the
[fixture provenance](../verification/results/rfc8448-fixture-provenance.json).
